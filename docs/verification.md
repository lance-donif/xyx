# Three.js 验证规程

这份规程把 Claude Code 团队的端到端测试、属性测试和差分测试用于短片、浏览器演示、游戏和可漫游空间。[文章原文](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

## 从验收动作反推证据

1. 按交付版本和本次改动选检查。先写清「用户从哪里开始 → 做什么 → 最后看到什么」、目标环境、必须保持的结果和判定门槛。改动说明或文件清单可用于选测试，结论取自实际运行结果。
2. 从可重复、成本低的检查开始。用播放器打开最终导出，用浏览器或设备仿真实际操作当前成品。准备清晰的启动入口和短路径，复杂真机矩阵与耗时评测留到提交或交付前。修复后从最早失败的步骤复验，再重走受影响的完整流程。
3. 每项记录交付版本或文件摘要、环境、实际操作或命令、输入、预期、实测结果和可定位的证据。失败时保留第一个偏离预期的步骤，以及截图、时间戳、读数或执行输出。注明证据来自亲测、他人可核对的运行记录或虚构样例。
4. 遇到工具不可用，先用可达到同一验收条件的运行方式继续。例如用浏览器直接点击，或让播放器打开导出文件并逐帧复核。收尾前逐项核对验收范围，完成仍可执行的检查。仍无证据的必检项标「未测」或「无人核实」，写清受阻原因。测试计划、启动成功和口头确认只能记录为各自的进度，实测通过必须有实际结果。

## 按改动选择测试

| 方法 | 何时用 | 怎么执行 |
| --- | --- | --- |
| **端到端测试** | 核心用户路径、发片、交付入口或集成有变化 | 若只能做一种验证，先跑这项。浏览器从打开成品到最后一步，点击或触摸，核对最终画面和状态。影片从打开最终 MP4 到实际播放，查指定时间段。记录步骤，失败就定位到第一个实际偏差及未到达的终点。 |
| **属性测试** | 有边界、往返、幂等或任何有效输入都该满足的约束 | 先固定不变量，再用多组输入主动找反例。覆盖临界值、重复操作、不同顺序、视口与时间基等相关变化。输入多时用固定种子生成，报告失败的种子和最短可复现序列。例如任意顺序切色后灯罩、按钮和提示一致，同一色重复选择后状态保持。 |
| **差分测试** | 重构、迁移、优化，或修复部分行为且其他行为应保持 | 固定可用的旧版、输入和环境，先记经确认允许变化的部分。新旧版用相同输入重跑，比较可见结果、状态或读数。按预先约定的口径消除无关差异，例如不影响画面的编码元数据。报告预期变化与额外差异。缺可用旧版时记录差分待证，继续做可执行的端到端或属性测试。 |

用触发条件管理验证项。每条写明「何种改动触发 → 验什么 → 到哪里找证据」，关联已有问题或验收要求。改交互与布局时检查已约定的完整路径和视口。改时间轴、导出或播放器时检查交付文件的显示时间与播放。改渲染材质与资源时按作品类型重测相关画面、帧时间或下载量。涉及兼容性的改动补一个已存在的项目、素材或状态作为输入。

## 保持验证独立

- 交付负责人定验收标准。使用基线分支或负责人冻结的规则、样本和预期结果。评审开始时固定候选版本，候选附带的规则改动另行核对授权。需要改变标准时，由负责人确认并显式记录，再用新标准复验。版本更新后给出针对新版本的证据。
- 每次结论由一个独立评审负责。后续评审沿用先前的失败路径和测量口径，检查当前成品。测试评审技能本身时，用空白会话、已知缺陷和干净对照。预期答案留给评估方，修改规则用过的样本之外保留独立用例，查看真问题有无漏报及正常样本有无误报。
- 首次失败和复验结果都要保留。每次重跑先说明要验证的诊断、已改动的因素或复现条件。出现时过时不过时追查根因，保留偶发失败的证据。跳过用例、延长固定等待、放宽门槛和重跑到绿都无法作为修复依据。如需退役不稳定用例，记录原因和替代覆盖，由负责人确认。
- 同一必检项经三轮有依据的诊断和修复仍失败时，把已知失败、复现动作、历次读数和下一项需人工判断的事交给负责人。可继续完成相互独立的检查。原有创作评审的两轮或五轮上限仍按作品范围执行。

## 让结果回到规则

验收报告附「已验证的版本 + 执行方法 + 结果 + 未验证项」。项目已有提交或发布记录时，可用同样的摘要标记已验或未验。已有门禁可用「关闭」「观察」「执行」模式管理。新门槛先以观察模式记录本会阻断的版本和原因，用真实问题与干净对照核对命中情况，再由负责人决定何时执行阻断，并记录放行例外与理由。

重复漏报或用户可复现的回归，先用旧版或留存成品复现，补一条可触发、可取证的检查，并用独立样本复验。定期合并重复项，清理失效规则，优先保留能抓到真实影响的检查。
